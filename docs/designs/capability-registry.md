# Design: Capability Registry — a self-updating map of research software modules across departments

## Problem Statement
Research groups across departments and organisations (starting with Maastricht legal-NLP / BISS projects) build overlapping software modules — search pipelines, case-law segmenters, citation extraction, annotation tooling — without knowing that a sibling project already produced a reusable piece. The user's framing: the cost is **missed reuse and collaboration**, not policing duplication. Today nobody checks ("they just rebuild"), so the overlap is invisible until after the fact.

The current artefact (`legal-nlp-workflow-builder.html` + `legal-nlp-projects.json`) is a single-file, localStorage-backed editor that models each project as rows of **component × data source × technique** it *uses* and *produces*, and computes weak / moderate / strong ties plus producer→consumer "supply" links between projects. It has 6 projects (Am AI Right, Lawnotation, BAIGLE, CLE, BlueLab, JusticeBot), no persistence beyond one browser, no automatic data, no public/admin split and no FAIR assessment.

## Demand Evidence
- User reports a **missed reuse / collaboration** pattern (a team built something it could have reused or co-developed). **The specific incident (projects, component, cost) was not named during the session — open evidence gap.**
- No one has yet paid, mandated or complained in a way we can cite. Treat demand as a hypothesis to validate (see The Assignment).

## Status Quo
"Nothing — they just rebuild." No one checks for existing modules before starting. Implication: the pain is invisible, so the product cannot rely on people coming to search; it must **push** overlaps to them, and its data must arrive without manual effort.

## Target User & Narrowest Wedge
- **Supply side / user #1: RSE or research-software lead** (e.g. at BISS or a faculty). Has GitHub admin access, a FAIR4RS motive, and the mandate to curate. Keeps the data true.
- **Demand side / payoff: PI or project lead** starting a project or writing a grant; needs "has anyone here built X?" at decision time and benefits from showing reuse/collaboration.
- **Public visitors** (partners, students, other universities): showcase audience, served second.
- **Narrowest wedge:** a nightly-harvested, curator-confirmed capability map of the configured GitHub orgs, with FAIR evidence per repo and a weekly overlap digest — no logins required to view.

## Constraints
- Pre-product; no sponsor commitment yet → minimal ops, near-zero hosting cost.
- Must survive the champion leaving (intrapreneurship reorg test).
- Data must not go stale without anyone noticing (catalogue staleness is the #1 failure mode in the landscape).
- Private repos exist (e.g. a repo that fails to sync); must degrade visibly, never silently.

## Premises (all agreed by user)
1. **P1 Push, don't wait.** The product pushes overlaps (alerts, weekly digest) rather than waiting for searches.
2. **P2 Auto-harvest + curate.** Data is harvested from GitHub orgs (README, CITATION.cff, codemeta.json, LICENSE, releases, topics, dependency manifests, Zenodo DOI); a suggestion engine (rules first, optional LLM) proposes module tags (component × data × technique), and the RSE confirms them. Manual entry alone goes stale.
3. **P3 Complement RSD, don't rebuild it.** The Netherlands eScience Center's Research Software Directory already serves Dutch universities at repo/product granularity. Our differentiator is the module-level capability graph, overlap/supply detection and FAIR evidence. Interoperate (codemeta / RSD export), do not compete on showcase pages.
4. **P4 FAIR4RS as an evidence scorecard,** listing automatable indicators with the file/URL that proves each — never a pass/fail "compliant" stamp.
5. **P5 RSE first, PI is the payoff;** the public view is a showcase built second.
6. **P6 Ship as a hosted (static) web app with a scheduled sync job,** not a localStorage HTML file.

## Landscape (Layer 1/2/3)
- Layer 1: Research Software Directory (eScience Center; Utrecht, Leiden, Groningen, Amsterdam UMC, Helmholtz) — harvests GitHub/Zenodo/Zotero, JSON API, self-hostable. JHU Open Source Catalog. howfairis (fair-software.eu 5 recommendations, GitHub Action). FAIRGuard (17 FAIR4RS principles, WIP).
- Layer 2: internal catalogues (Backstage et al.) fail via manual fields that go stale, no accountable owner, and loss of trust.
- Layer 3 / EUREKA (hypothesis, not yet verified): the directories surfaced in the search (RSD, JHU catalogue, university RSD instances) describe software at repo/product granularity (descriptions, keywords, mentions, organisations). None that we checked models module-level uses/produces with data × technique. **Verification is part of The Assignment** (inspect RSD's data model: keywords, research domains, related software). If confirmed, the defensible product is an auto-inferred, curator-confirmed capability graph that pushes overlaps and sits beside RSD.

## Approaches Considered
### Approach A: Git-backed static registry (CHOSEN)
GitHub repo is the database. A scheduled GitHub Action harvests configured orgs, computes FAIR indicators, generates module suggestions (rules first, LLM optional) and posts them to a curation queue. A static public site renders projects, modules, relations and FAIR evidence. Curators use GitHub in Phase 1 and an in-browser admin UI in Phase 3. Alerts and a weekly overlap digest. Effort (rough guess) for the core: L, about human ~8-10 weeks / CC ~4-6 days. The accepted expansions E1–E6 add about human ~5-7 weeks / CC ~2-3 days. Total XL, about human ~13-17 weeks / CC ~6-9 days across 3 phases [estimated]. Risk Medium, driven by privacy, auth, credential ownership and the E2 page weight.
### Approach B: Full web platform — rejected for now
Postgres + API + worker + GitHub App + SSO + roles + semantic search. Best long-term shape but needs hosting, owner and ops budget before a sponsor exists. Schema in A is designed to migrate here.
### Approach C: RSD + capability sidecar — rejected for now
Reuses RSD for showcase/editing; splits curator work across two systems and binds to RSD's roadmap. Kept as an integration target (export), not the base.

## Recommended Approach
Approach A, because the user is pre-product and needs a sponsor demo quickly with minimal ops. Its "survives a reorg" property holds only if every credential is institution-owned (see Ownership). **Launch scope: the legal-NLP / BISS GitHub orgs only.** Other departments come after the taxonomy-growth process has been proven.

### Data model (JSON in a public data repo, schema-versioned, validated in CI)
- `taxonomy.json`: dataSources, techniques, components (migrated from the existing file). Terms carry `status: active|proposed`.
- `orgs.json`: harvest config.
  - Lists orgs and per-repo overrides: `visibility: include|private-listed`.
  - Private repos that aren't listed are never named in the public repo. Any exclusion list lives in `registry-private`.
  - Per org: `fixit: {enabled, consent_by, consent_date}`. Only an **org owner** can give consent, by installing the fix-it App. A curator then records that consent here.
- `projects/<id>.json` (curator-owned): `id, name, type (software|research), department, leads[] {display_name, github?, contact_id}, repos[], uses[], produces[], status`. Rows keep the current shapes. A produces row is `{id, comp, datas[], techs[]}`. A uses row is either inline `{id, comp, datas[], techs[]}` or a reference `{id, src:{proj,row,data?}}` that resolves to another project's produces row. Mirroring rule, carried over from `mirrorProduces`: a software project automatically uses what it produces.
- **Contact data stays private (GDPR).** Personal email addresses are never stored in the public repo. `contact_id` points into a contacts file held in a private `registry-private` repository. That repo is readable only by the notification workflow and by `registry-curators`. Leads opt in to notifications, and that consent is recorded with their contact entry. Notification opt-in and **listing consent** are recorded separately in `registry-private`. Until a lead consents to listing, their public `leads[]` entry holds only `contact_id`. `display_name` and `github` are written to the public file only after listing consent is recorded. A lead without notification opt-in gets no email.
- `harvest/<owner>__<repo>.json` (machine-owned): metadata, FAIR evidence, `project: <id>|null`, suggestions, `sync: {state, error_class}`.
- `harvest/fixit.json` (machine-owned): per repo, open, merged or closed fix-it PRs and licence issues. A PR closed by a maintainer is never reopened. Closures are found by the nightly harvest polling PR state.
- `curation/decisions.json` (curator-owned): accepted and rejected suggestions, keyed by `repo + suggestion hash`, with the content hash of the README and manifests they were judged against.
- `relations/last-build.json` (**kept in `registry-private`**, outside voice #6): the relations as of the previous build. The build bot advances it after each build so alerts never re-fire. It's committed only when its content changes, and it contains no timestamps or run ids. The build workflow's push trigger has a `paths-ignore` for `relations/**` and `status/**`, so a baseline or heartbeat push never starts another build.
- `relations/week-start.json` (**kept in `registry-private`**): the baseline for the weekly digest. At diff time the digest job records the commit SHA of the `last-build.json` it compared against. After a successful send, it sets `week-start.json` to **that exact snapshot**, not to whatever `last-build.json` holds by then.
- **The validator gates every write path, not just PRs.**
  - `main` is protected and requires the validator status check, so curator edits made in the web editor land through an auto-merging PR that merges only when validation passes.
  - The institution's GitHub App is the **only actor on the `main` ruleset bypass list**. All bot writes push directly to `main` using the App token: harvest files, curation-queue applications, relation baselines and the heartbeat. Because the bypass skips the status check, every bot push follows the same loop: **fetch, rebase onto `main`, re-run the validator, push**. It retries up to 3 times on non-fast-forward. If validation fails or retries run out, it aborts and opens an issue. Humans never bypass.
  - The build validates again (in Phase 1 the "build" is the relations, digest and alerts job; from Phase 2 it also builds the site). On failure it keeps the last good output and opens an issue.
  - Failures include schema errors, dangling `src` references (a referenced produces row was deleted) and unknown taxonomy ids.
- **Migration:** a one-time script splits `legal-nlp-projects.json` into these files. It keeps the existing ids (`p_*`, `r_*`), drops the UI-only `current` field, and checks that the migrated data produces the same ties and supply links as the current tool. The source has no `department`, `leads` or `repos`. Those fields start empty, and the validator **warns** rather than fails on them. A one-off backfill checklist goes into the Curation queue. The department report (E5) buckets repos into "Unassigned project" and "No department" until they're filled.

### Repo → project lifecycle
1. The harvester finds a new repo in a configured org and writes a harvest record with `project: null`. That puts it in the **unassigned queue**.
2. Unassigned repos appear publicly with metadata and the FAIR scorecard, but no modules. They are listed in the RSE's weekly queue.
3. The RSE assigns the repo to an existing project or creates a new project file.
4. Suggestions attach to the assigned project:
   - **produces** suggestions come from what the repo implements: README, topics and package exports.
   - **uses** suggestions come from dependency manifests. When a repo depends on a package published by another registry repo, the harvester suggests a `src` reference to that project's produces row.
5. **Phase 1 curation runs through a rolling "Curation queue" issue, maintained by the bot.**
   - Each run, the bot rewrites the issue: one task-list block per suggestion, with `accept` / `reject` checkboxes and the evidence for it.
   - A workflow triggered by `issues: edited`, and limited to members of `registry-curators`, applies the ticked items:
     - accepted items become rows in `projects/<id>.json`
     - accepted and rejected items are both written to `curation/decisions.json`, with the README and manifest hashes filled in automatically
   - It commits through the validated path. Curators never hand-edit hashes.
   - A rejected suggestion resurfaces only if those hashes change.

### Harvester (GitHub Action: nightly plus manual dispatch)
- Runs as an institution-owned **GitHub App** installed on the configured orgs. It uses the REST/GraphQL APIs and a Zenodo DOI lookup.
- **Machine-owned files are auto-committed to main by the bot**, so FAIR evidence and sync errors never wait on a human merge. Nothing is committed when content hashes are unchanged, which means no nightly churn. The "last checked" time comes from the workflow run and is stamped in at site build, not committed.
- Only module suggestions and taxonomy proposals need review.
- **Suggestion engine, default no-LLM mode:**
  - map GitHub topics to taxonomy terms
  - map dependency manifests to techniques (e.g. `transformers` → BERT/LLM, `networkx` → network analysis)
  - match README text against curated keyword lists per taxonomy term
- **Optional LLM mode** turns on only after the provider is approved under university data policy. It sends only the README of a **public** repo plus the names in its manifest. It never sends source code and never touches private repos.
- New terms suggested by the engine are written as `status: proposed` in `taxonomy.json` and approved by the RSE. The RSE owns the taxonomy.

### Public logs and private data
- The data repo's Actions logs are public.
- **The notification, send-ledger and consent workflows run in `registry-private`**, never in the public repo. They read the public data through the App token.
- The harvester logs only listed repo names and error classes. It never logs README text, unlisted private repo names, email addresses or bounce text.
- Secrets are masked. Unhandled exceptions are caught and logged with their class only.

### Private and inaccessible repos (visibility policy)
- The data repo and the site are public.
- By default only public repos are harvested.
- A private repo is shown only if it's explicitly marked `private-listed`. In that case the record holds only name, owning project and "private, details withheld". No README content, suggestions or FAIR evidence are stored, and nothing is sent to an LLM.
- Sync errors are stored as error classes such as `not_found`, `forbidden`, `rate_limited` or `auth_expired`. Raw error text is never stored.
- The card shows the error class and the last-good date.

### FAIR4RS scorecard
Automatable indicators, each with a link to the file or URL that proves it:
- licence
- CITATION.cff
- codemeta.json
- a DOI-bearing release
- registry presence
- README and docs
- install instructions
- tests/CI
- versioned releases
- declared dependencies
- contributing guide
- recent activity

Principles that can't be checked automatically are shown as "needs curator attestation". This is an evidence scorecard, never a "compliant" stamp.

### Relations engine
Refactor `computeTies`/`computeSupply`/`resolveRow`/`projInfo`/`rowKeys`/`mirrorProduces` into pure functions that take the project set as an argument and run in Node (build) and in the browser. Tests on the 6 current projects must reproduce the existing tool's output exactly.

### Push: alerts and digest
- **Alerts (event-driven):** every build after a push to `main` recomputes ties and supply links from all project files and diffs them against `relations/last-build.json`. It doesn't matter which edit caused the change: an accepted uses or produces row, a `src` reference, an assignment, or a direct edit. Changes that trigger an alert:
  - a new project pair
  - a pair whose tie level goes up
  - a new supply link

  For each change, the opted-in leads of both projects get an email straight away. Sending is tracked per alert item and per recipient in a send ledger in `registry-private`.
  - A retry sends only what's missing, so nobody gets duplicates.
  - Failure classes, per transport:
    - **Temporary:** SMTP 4xx, connection errors, HTTP 429/5xx. The baseline stays where it is and the next build retries. After 2 consecutive failed builds, an issue @-mentions `registry-curators`.
    - **Permanent, per recipient:** SMTP RCPT 5xx, or a per-recipient rejection from the HTTP API. That recipient is marked `skipped` and the contact is flagged `failing`.
    - **System failure:** SMTP auth or relay rejection (e.g. 535), or HTTP 401/403. Nobody is skipped, the baseline stays where it is, and a curator issue opens straight away.
  - Public issues name only the `contact_id` and the error class, never an address or bounce text.
  - `last-build.json` advances once every item is either sent or skipped.
- **Weekly digest:** emails each opted-in project lead the diff between `week-start.json` and `last-build.json` for their projects. It uses the same per-recipient send ledger and failure classes as alerts, and `week-start.json` advances only once every recipient is sent or skipped. The RSE also gets a rolling GitHub issue with the full diff and the curation queue.
- **Outcome capture without a server:**
  - Each digest or alert item carries a "this led to contact / reuse" link. It opens a prefilled GitHub issue form (`outcome.yml`, with the pair and tie in the URL).
  - For leads without a GitHub account, there's a prefilled `mailto:` link to the RSE mailbox instead.
  - The bot files outcome issues into `curation/outcomes.json`. The RSE logs mailed outcomes by hand.
- Email goes through an institutional SMTP relay or a transactional mail service.

### Views
- **Public site:** static build from the JSON (wireframe below). Built after every harvest and every merge.
- **Admin/staff — Phase 1:** curators work through GitHub itself. Suggestions are accepted or rejected in the bot-maintained Curation queue issue. Manual edits go through the GitHub web editor, which opens a PR. A `curator-automerge` workflow enables auto-merge **with the harvester App token**, not `GITHUB_TOKEN`, on PRs opened by members of `registry-curators`, so the merge still triggers the build and alerts. A scheduled hourly guard also runs the build if the current commit on `main` hasn't been built yet. The PR merges only once the validator passes. Other staff propose edits through PRs or an issue form, and a curator reviews them.
- **Admin/staff — Phase 3:** an in-browser admin UI, which needs a small OAuth token-exchange function. That is the one piece of hosted infrastructure. It runs on institutional serverless hosting under the institution's account.

### Ownership (reorg-proof)
- **Two GitHub Apps, both institution-owned:**
  - `registry-harvester` is **read-only on the harvested orgs**: `metadata:read`, `contents:read`, `pull_requests:read` (to poll fix-it PR state), and org `members:read` (for the `registry-curators` check).
  - On the **data repo only** it has `contents:write`, `issues:write`, `pull_requests:write` (to enable auto-merge) and `actions:write` (to dispatch builds). It's the only bypass actor on `main`.
  - On `registry-private` it has `contents:write` for the send ledger and consent records.
  - It enables auto-merge for curator PRs and triggers builds with its own token.
  - `registry-fixit`: `contents:write`, `pull_requests:write`, `issues:write`. Installed **only by owners of opted-in orgs**. It's never a bypass actor and never touches the data repo.
- The OAuth app, the mail-service credentials and the LLM key also belong to an institutional GitHub org or service account, never a personal one.
- Secrets live in org-level Actions secrets.
- If a credential expires or fails, the harvest fails loudly: a red "data stale since <date>" banner on the site, plus an issue that @-mentions `registry-curators`.
- **Detecting a job that never runs:**
  - Each successful harvest run writes and commits `status/heartbeat.json` (its success timestamp), **every night**, even when nothing else changed. That's one tiny commit a day, which is an accepted cost. It also keeps GitHub from auto-disabling the schedule after 60 days of repository inactivity.
  - The public site checks heartbeat age in the browser on page load. If the last successful harvest is more than 3 days old (three missed nightly runs), it shows the stale banner, even if no workflow has run since.
  - The weekly digest workflow is a separate schedule. It checks the heartbeat too and emails the RSE if it's stale.

### Detailed specifications (amended by the CEO spec review; these take precedence)
- **FAIR evidence detection rules.** Each indicator records `{met, evidence_url}`.
  - licence: a SPDX-detectable `LICENSE*` file, per GitHub's license API
  - citation: `CITATION.cff` parses
  - metadata: `codemeta.json` parses
  - persistent identifier: a release with a Zenodo DOI, from the GitHub–Zenodo concept DOI lookup
  - registry presence: a PyPI/CRAN/npm package whose metadata (project URLs, `URL:`, `repository`) points back to this repo, or a Software Heritage origin for the repo URL. From Phase 2, an RSD listing found by the E6 lookup also counts. Same-named packages that don't point back don't count.
  - README and docs (one indicator): README ≥ 500 characters, and a `docs/` folder or docs URL is recorded as supporting evidence
  - install instructions: README has an "install" or "installation" heading, or contains `pip install`, `npm install`, `conda` or `docker`
  - tests/CI: a `tests/` or `test/` folder, or a CI workflow file
  - versioned releases: at least one semver tag
  - declared dependencies: a manifest exists (pyproject, requirements, package.json, DESCRIPTION, environment.yml)
  - contributing: `CONTRIBUTING*` exists
  - recent activity: a commit on the default branch within the last 12 months
- **E1 fix-it PRs.**
  - Phase 1 generates `CITATION.cff` and `codemeta.json` only.
  - Authors come **only from public metadata already in the repo** (codemeta, `.zenodo.json`, package author fields). If there isn't any, the file is **not generated**; the request to add authors goes into an issue instead. Commit history is never mined for names. Every generated file is validated against the CFF schema (cffconvert) and the codemeta JSON schema before a PR is opened.
  - A missing licence gets an issue asking the owner to choose, with a link to the university's licence guidance. No LICENSE file is ever generated (D16).
  - At most one open fix-it PR per repo. Dry-run mode logs what it would open.
- **E2 natural-language search.**
  - Model: a pinned, quantised ONNX sentence-embedding model.
    - Candidates: all-MiniLM-L6-v2 (English, ~23 MB) and a multilingual MiniLM variant.
    - The fixtures decide: pick the smallest model that gets 8 of 10 fixture queries right, including Dutch and French ones, within a 50 MB budget. If none qualifies, ship keyword plus facet search only.
    - The model and the ONNX runtime WASM files are **served from the Pages site**, never fetched from the Hugging Face Hub. The SHA-256 is checked at build time and when the browser loads the model.
  - Document text per module: the module row's labels, plus the repo description and the first 1,000 characters of a public README.
  - The query runs in the browser with the same model, through transformers.js. The model is **lazy-loaded on the first natural-language query** and cached.
  - Budget: index ≤ 2 MB and model ≤ 50 MB, lazy-loaded; nothing extra on first page load.
  - Fallback: if the model fails or the connection is slow (no load within 8 s), keyword plus facet search.
  - Fixtures: 10 queries over the 6 migrated projects, at least 3 of them in Dutch or French, each with its expected top-3, written as JSON test cases.
- **E5 badges.** The canonical list has **12 automatable indicators** (the list above; README and docs count as one), so m = 12. The badge reads "FAIR evidence: n of 12 automatable" and links to the scorecard. Indicators that need curator attestation are not counted. Private-listed repos get no badge. The department report shows coverage per indicator, sorted by indicator, with no ranking of departments.
- **E6 interop.**
  - The RSD lookup is a Phase 2 harvest step. Pre-fill values become **suggestions in the Curation queue** and are never written directly into curator files.
  - codemeta is emitted per repo, plus a project-level aggregate. `registry.jsonld` excludes private-listed repos and every lead identifier.
- **Curation queue mechanics.**
  - Each queue issue holds at most 40 items, well under GitHub's 65,536-character body limit. Overflow goes to numbered follow-on queue issues, oldest first.
  - **Curators act by commenting**, e.g. `/accept <hash>` or `/reject <hash>`, or with a checkbox tick.
    - A short capture job runs **outside any concurrency group**. On `issue_comment` or `issues: edited`, it reads the command, or the tick diff between `issue.body` and `changes.body.from`, and appends it to `curation/pending-actions.jsonl` right away.
    - Ticks and comments therefore survive any later rewrite of the issue body.
  - Only the apply step and the queue-rewrite step share the `registry-queue` concurrency group. The harvest and heartbeat jobs are never in it.
  - The rewrite runs every pending action first, then regenerates the issue.
  - Apply is idempotent, keyed by suggestion hash.
  - The apply workflow ignores edits made by the bot.
  - It checks team membership with the harvester App token.
  - The nightly rewrite first applies any ticked but unapplied items, then rewrites the issue.
  - Applied items are removed from the queue.
- **Outcome capture.**
  - Outcome issues come from the form with the `outcome` label, and are recorded only after a curator adds `confirmed`.
  - The public `curation/outcomes.json` holds only the project pair, the tie and the date. No names.
- **Build concurrency.** All builds share the `registry-build` concurrency group with `cancel-in-progress: false`, so baseline updates happen one at a time.
- **Lead listing consent (GDPR).**
  - Display names and GitHub handles are published only once the lead has agreed. That happens when the RSE onboards them, and the consent is recorded in `registry-private`.
  - On a removal request, the lead is removed from the current files and builds. Git history isn't rewritten; this limitation is stated in the privacy notice.
- **Package → registry mapping (uses suggestions).**
  - The producer's package name comes from `pyproject [project].name`, `package.json name` or `DESCRIPTION Package`.
  - If the target project has several produces rows, the suggestion lists them all for the curator to choose from.
  - If it has none, it suggests a new produces row on the target project.


### Section 4: Data Flow & Interaction Edge Cases
```
  INPUT(repo via API) → VALIDATE(schema of API response) → TRANSFORM(FAIR rules, suggestions)
      → PERSIST(harvest/<node_id>.json via push loop) → OUTPUT(queue, relations, site)
  shadows: nil field → "absent"; empty repo → state=empty; wrong type in CITATION.cff → CffParseError;
           README > 1 MB → truncate to first 1,000 chars for E2, rules scan first 200 KB;
           timeout → unknown; conflict on push → rebase+revalidate; non-UTF-8 README → decode with
           replacement, flag "encoding"; renamed repo → same node_id, name updated (A2)
```
**Async ordering.** The invariant is that `main` never contains a dangling `src` reference or an invalid project file.
```
  time │ curator PR (delete produces r_x)   │ bot apply (/accept uses src→r_x)  │ main state
  t1   │ PR validated (r_x unused yet) ✓     │ capture /accept → pending log      │ r_x exists
  t2   │ auto-merge → main                   │                                    │ r_x deleted
  t3   │                                     │ fetch+rebase onto main, revalidate │ dangling → FAIL
  t4   │                                     │ abort, comment "r_x no longer exists" │ main valid ✓
  reverse order: bot pushes src→r_x first; curator PR's required check re-runs on the merge
  queue/base update → fails "r_x referenced by p_y" → PR blocked ✓  (requires a GitHub **merge queue** on `main`, which revalidates each PR against the latest main; outside voice #5)
```
The mechanisms that keep this safe are the bot's revalidation before every push and the merge queue. Regression proof is an integration test with controlled pause and release points, run in both orders.

| INTERACTION | EDGE CASE | HANDLED? | HOW |
|---|---|---|---|
| Queue tick or comment | accept and reject both given | Y | ConflictingActions, no-op plus comment |
| Queue tick | double tick or replayed event | Y | Apply is idempotent by suggestion hash |
| Queue | 0 suggestions | Y | The issue says "Queue empty, last run <date>" |
| Queue | more than 40 items | Y | Follow-on issues |
| Search (E2) | empty query | Y | Shows all projects, sorted by activity |
| Search (E2) | no results | Y | "No matches. Try a broader term", with facet suggestions |

**Gap found:** nothing revalidated PRs against the latest `main`. It's fixed with a **merge queue**, not "require branches up to date" (outside voice #5: nightly heartbeat commits would block curator PRs).

### Section 7: Performance
- **API cost:** one GraphQL query per repo fetches metadata plus the contents of the files we check via `object(expression:"HEAD:<path>")`. Repos are batched 20 per query, and conditional requests use `pushedAt` to skip unchanged repos.
  - ~40 repos: about 2 queries a night.
  - 4,000 repos: about 200 queries, well within the 5,000 points/hour per installation [estimated].
- **Memory:** harvest records are about 5 KB each [estimated]. 4,000 repos is about 20 MB, which is fine.
- **E2 index:**
  - Rough estimate: 384-dim int8 vectors × (modules + repos), about 0.4 KB each.
  - 4,000 repos × 3 modules is about 5 MB, over the 2 MB budget.
  - Remedy: shard the index by department and lazy-load it; required by the budget.
- **Site build:** about 1 minute for 40 repos; under 10 minutes at 4,000, including embeddings on CPU [estimated].
- **Slowest paths:** (1) first E2 query, a model download of up to 50 MB, once and cached; (2) the nightly harvest; (3) the E4 layout, which is precomputed at build.
- **No DB or connection pool concerns.**
- **Findings:** 1 (E2 index sharding at scale). Required by the approved budget, so it's recorded.

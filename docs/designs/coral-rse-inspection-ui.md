## Problem Statement

The BISS Capability Registry (`index.html` + `data/registry.json` + `status/heartbeat.json`) maps 6 legal-NLP research and software projects (`Am AI Right`, `Lawnotation`, `BAIGLE`, `CLE (Case Law Explorer)`, `BlueLab`, `JusticeBot`) across a 3-axis module taxonomy (`components × dataSources × techniques`) and computes pairwise overlap ties (`strong`, `moderate`, `weak` via `computeTies()`) plus producer-to-consumer supply links (`computeSupply()`).

While the Hallmark Coral visual redesign in `index.html` (and reference stylesheets `tokens.css` and `base.css`) established a restrained, warm-paper editorial aesthetic using OKLCH design tokens (`--color-cotton`, `--color-desk`, `--color-paper`, `--color-print`, `--color-accent`, `--color-accent-2`, `--color-focus`) and typography (`--font-display: "General Sans", ui-sans-serif, system-ui, sans-serif`, `--font-outlier: "Geist Mono", ui-monospace, monospace`), the application remains a largely static three-tab view (`#v_projects`, `#v_relations`, `#v_catalogue`) that hides or leaves unclickable critical data already present in `data/registry.json`:

1. **Hidden repository links and curation gaps (`p.repos`):** PR #13 (`b45ac48`) populated `repos` in `data/registry.json` for `Lawnotation` (`p_9klfx`, 6 GitHub repositories under `MaastrichtU-BISS/*`) and `CLE (Case Law Explorer)` (`p_sskx9`, 13 GitHub repositories: `https://github.com/maastrichtlawtech/case-law-explorer` plus 12 `https://github.com/MaastrichtU-BISS/*` repositories, totaling 19 linked repositories across 2 projects), while 4 of the 6 projects (`Am AI Right`, `BAIGLE`, `BlueLab`, `JusticeBot`) still lack linked repositories (tracked in GitHub Issue #7). `index.html` (`renderProjectDetail()`) never renders `p.repos`, leaving both the 19 linked repositories and the 4 unlinked projects invisible in the UI.
2. **Incomplete and non-interactive supply-chain provenance (`r.src`):** In `data/registry.json`, `uses` rows can reference a `produces` row via `r.src` (`{ proj, row, data? }`). In `#v_projects`, `rowTable(p, 'uses')` renders `<span class="fromtag">From ${esc(srcLbl)}:</span> ${comboLabel(rr)}` (`From this project:` when `r.src.proj === D.current`, or `From ${srcP.name}:` when imported from another project), but this `.fromtag` is static text that cannot be clicked to pivot to the upstream producer project, and `rowTable(p, 'produces')` renders zero downstream provenance showing which other projects consume a produced row (`-> supplies {ConsumerProject(s)}`).
3. **Dead taxonomy and relation labels:** In `#v_catalogue` (`renderCatalogue()`), `#catData .citem`, `#catTech .citem`, and `#catComp .citem` display usage badges (`${n} use(s)`, `${n} proj`, or `${n}`), and in `#v_projects` / `#v_relations`, `.rowtable` cells (`.dchip`, `.tchip`, `.ct`) and `.edgetable` rows name specific taxonomy items and projects. Clicking any of these items does nothing: an RSE cannot click `Case law – NL` (`3 use(s)`) or `Search` (`3 proj`) to filter and inspect which projects and module rows account for that count.

### Technical Specification

#### 1. Visual Design System Lock (`index.html`, with `tokens.css` & `base.css` as reference artifacts)
- **Theme & Palette:** Hallmark Coral (`light/grotesk-sans/warm`, restrained posture) defined inline in `index.html`'s `:root` block:
  - Surfaces: `--color-desk: oklch(94.3% 0.008 64)`, `--color-cotton: oklch(98.8% 0.0045 80)`, `--color-paper: oklch(97% 0.006 55)`, `--color-paper-2: oklch(94.5% 0.007 55)`, `--color-paper-3: oklch(91.5% 0.009 55)`.
  - Text & Ink: `--color-print: oklch(23% 0.012 38)`, `--color-ink: oklch(21% 0.012 38)`, `--color-ink-2: oklch(29% 0.013 40)`, `--color-muted: oklch(47% 0.013 45)`.
  - Rules & Accents: `--color-rule: oklch(87% 0.009 55)`, `--color-rule-2: oklch(81% 0.011 55)`, `--color-accent: oklch(74% 0.125 30)`, `--color-accent-2: oklch(54% 0.165 29)`, `--color-focus: oklch(54% 0.17 30)`, `--color-error: oklch(52% 0.19 27)`, `--color-success: oklch(50% 0.12 150)`.
- **Typography:** `--font-display: "General Sans", ui-sans-serif, system-ui, sans-serif`, `--font-body: var(--font-display)`, `--font-outlier: "Geist Mono", ui-monospace, monospace` with `font-variant-numeric: tabular-nums` on counts and badges.
- **Stylesheet Architecture:** Styles remain inline in `index.html`'s `<style>` tag so the page loads with zero render-blocking stylesheet requests and satisfies the existing CSP (`style-src 'self' 'unsafe-inline'`); any new token or rule added to `index.html` is mirrored in `tokens.css` / `base.css`.

#### 2. Repository Provenance & Issue #7 Curation Strip
- **URL Validation Helper (`safeRepoUrl(rawUrl)`):**
  - Parses `String(rawUrl || '').trim()` inside a `try { const u = new URL(s); ... } catch { return null; }`.
  - Accepts **only** `u.protocol === 'https:'` with a non-empty `u.hostname`.
  - Returns `{ href: u.href, label }` where `label` strips leading `https://github.com/` (or `https://`) and trailing `/`, so `https://github.com/MaastrichtU-BISS/lawnotation` displays as `MaastrichtU-BISS/lawnotation`.
  - Any malformed or non-`https:` entry in `p.repos` returns `null` and is silently ignored when constructing `validRepos = (p.repos || []).map(safeRepoUrl).filter(Boolean)`. No anchor or warning badge is rendered for invalid entries; a project whose `p.repos` is absent, empty, or contains only invalid URLs has `validRepos.length === 0`.
- **Header Repo Coverage Indicator (`#repo-coverage`):**
  - Rendered inside `<header>` alongside `<nav class="tabs">` as `<div class="repo-cov" id="repo-coverage">`: displays `Repos linked: X / Y projects (Z repos)` (for current `data/registry.json`: `Repos linked: 2 / 6 projects (19 repos)`), where `X` is the count of projects with `validRepos.length > 0`, `Y` is `D.projects.length`, and `Z` is the sum of `validRepos.length` across all projects.
- **Per-Project Repo Strip (`.project-repos`) in `#projDetail`:**
  - Rendered inside `renderProjectDetail()` immediately below `.pdetail-h` (and `.pdesc` if present), before the `Produces` `.rowsec`:
  - **Note on class names:** Uses `.project-repos`, `.repo-label`, `.repo-chip`, and `.repo-missing` (never `.pill`, preserving `tests/e2e/edge-fixtures.spec.ts`'s `page.locator('#projDetail .pill')` single-element assertion).
  - **When `validRepos.length > 0`:** Renders `<div class="project-repos"><span class="repo-label">GitHub Repos (${validRepos.length}):</span>` followed by `<a class="repo-chip" href="${esc(r.href)}" target="_blank" rel="noopener noreferrer">${esc(r.label)}</a>` for each entry in `validRepos`.
  - **When `validRepos.length === 0`:** Renders `<div class="project-repos"><span class="repo-label">GitHub Repos (0):</span><span class="repo-missing">No repos linked yet — Issue #7</span></div>`.

#### 3. Inline Module Supply-Chain Provenance (`rowTable` in `#projDetail`)
- **Dangling Reference Safety (`resolveRow(r) === null`):**
  - Both upstream and downstream provenance checks require the producer project (`srcP = D.projects.find(x => x.id === r.src.proj)`) **and** the target produced row (`rr = resolveRow(r)`) to exist (`srcP && rr !== null`).
  - When `r.src` points to a deleted row (`resolveRow(r) === null`, as in `Orphan Consumer` in `tests/e2e/edge-fixtures.spec.ts`), `rowTable(p, 'uses')` renders the existing non-interactive `<span class="fromtag">From ${esc(srcLbl)}:</span> <span class="ct">(removed)</span>` and `consumersOfRow()` ignores the dangling reference.
- **Upstream Provenance on `uses` Rows (`r.src`):**
  - When `which === 'uses' && r.src`:
    - If `r.src.proj !== p.id && srcP && rr !== null`: renders `<span class="fromtag is-link" role="button" tabindex="0" data-filter-kind="proj" data-filter-id="${esc(srcP.id)}" title="Inspect ${esc(srcP.name)}">From ${esc(srcP.name)}:</span> ${comboLabel(rr)}`. Activating this `.fromtag` (click or `Enter`/`Space`) selects and filters by `{ kind: 'proj', id: srcP.id, label: srcP.name }`.
    - If `r.src.proj === p.id` (self-supplied) or `rr === null`: renders the non-interactive `<span class="fromtag">From ${esc(srcLbl)}:</span> ${comboLabel(rr)}`.
- **Downstream Provenance on `produces` Rows:**
  - Helper `consumersOfRow(producerProjId, producedRow)`: inspects all other projects `other` (`other.id !== producerProjId`) and collects each `other` that has at least one `u` in `other.uses` with `rr = resolveRow(u)` non-null where either (a) `u.src && u.src.proj === producerProjId && u.src.row === producedRow.id` OR (b) `rowKeys(rr).some(k => rowKeys(producedRow).includes(k))`; returns an array of unique consumer projects deduplicated by project ID.
  - When `which === 'produces'` and `consumers = consumersOfRow(p.id, r)` is non-empty:
    - Renders inside the first `<td>` (after `esc(compName(r.comp))`) a `<span class="suppliestag">→ supplies ` followed by each consumer project as `<span class="proj-link" role="button" tabindex="0" data-filter-kind="proj" data-filter-id="${esc(c.id)}">${esc(c.name)}</span>` (comma-separated) and `</span>`.

#### 4. Click-to-Pivot Faceted Filtering, Taxonomy Matching & URL Hash State
- **No `<button>` or `[onclick]` Control Pollution:**
  - To satisfy `tests/e2e/registry.spec.ts` (`'no editing, import, reset or example controls exist on any tab'`), all interactive filter chips, provenance links, Catalogue items, and the `#clear-filter` action are rendered as `<span>` or `<div>` elements with `role="button" tabindex="0"` and `data-filter-kind` / `data-filter-id` attributes, handled via a single delegated `click` and `keydown` (`Enter` / `Space`) listener on `document.body` (plus `Escape` on `window`). No `<button>` elements (beyond the 3 existing `.tab` buttons) and no `[onclick]` HTML attributes are ever added to the DOM.
- **Filter State Model & URL Hash Grammar:**
  - `activeFilter = null | { kind: 'comp' | 'data' | 'tech' | 'proj', id: string, label: string } | { kind: 'pair', a: string, b: string, label: string }`.
  - **URL Hash Grammar:** `#<view>` or `#<view>?filter=<kind>:<id>` where `<view>` is `projects`, `relations`, or `catalogue`, `<kind>` is `comp | data | tech | proj`, and `<id>` is `encodeURIComponent(id)`.
  - Parsed on startup (after `load()`) and on `window` `hashchange`: validates `<kind>` and checks that `<id>` exists in `D.components` (parent or sub), `D.dataSources` (parent or sub), `D.techniques`, or `D.projects`. Unknown or malformed filter parameters are ignored (`activeFilter = null`) without throwing.
- **Exact Taxonomy Matching Rule (`rowMatchesFilter(rr, activeFilter)`):**
  - Given a resolved row `rr` (`resolveRow(r)` for `uses`, or `r` for `produces`; returns `false` if `!rr`):
    - `kind === 'comp'`: returns `true` if `rr.comp === activeFilter.id`, OR if `activeFilter.id` is a parent component `c` in `D.components` and `(c.subs || []).some(s => s.id === rr.comp)`.
    - `kind === 'data'`: returns `true` if `(rr.datas || []).includes(activeFilter.id)`, OR if `activeFilter.id` is a parent data source `ds` in `D.dataSources` and `(ds.subs || []).some(s => (rr.datas || []).includes(s.id))`.
    - `kind === 'tech'`: returns `true` if `(rr.techs || []).includes(activeFilter.id)`.
  - Given a project `p`, `projectMatchesFilter(p, activeFilter)`:
    - For `kind === 'comp' | 'data' | 'tech'`: returns `true` if any row in `p.uses.map(resolveRow).filter(Boolean)` or `p.produces` satisfies `rowMatchesFilter(rr, activeFilter)`.
    - For `kind === 'proj'`: returns `true` if `p.id === activeFilter.id` OR if `computeSupply().some(s => (s.from === activeFilter.id && s.to === p.id) || (s.to === activeFilter.id && s.from === p.id))` OR `computeTies().some(t => (t.a === activeFilter.id && t.b === p.id) || (t.b === activeFilter.id && t.a === p.id))`.
- **Interactive Triggers Across All 3 Views:**
  1. **In `#v_catalogue` (`renderCatalogue()`):**
     - Preserves `#catData .citem`, `#catTech .citem`, and `#catComp .citem` with `.nm` and `.use` children and their exact text formats (`${n} use(s)` in `#catData` and `#catTech`, `${n} proj` on parent rows in `#catComp`, and `${n}` on `.citem.sub` rows in `#catComp`).
     - **Clickability, IDs, and labels by category:**
       - `#catData`: top-level parent `.citem[data-ds]` rows have no `.use` child and remain non-interactive category headers. Sub-item `.citem.sub[data-ds][data-sub]` rows with `subUsage(s.id) > 0` receive `role="button" tabindex="0" data-filter-kind="data" data-filter-id="${s.id}"` and produce `label = "${ds.name} – ${s.name}"`.
       - `#catTech`: top-level `.citem[data-t]` rows with `techUsage(t.id) > 0` receive `role="button" tabindex="0" data-filter-kind="tech" data-filter-id="${t.id}"` and produce `label = t.name`.
       - `#catComp`: top-level `.citem[data-c]` rows with `compUsage(c.id) > 0` receive `role="button" tabindex="0" data-filter-kind="comp" data-filter-id="${c.id}"` and produce `label = c.name`; sub-item `.citem.sub[data-c][data-sub]` rows with `compUsage(s.id) > 0` receive `role="button" tabindex="0" data-filter-kind="comp" data-filter-id="${s.id}"` and produce `label = "${c.name} – ${s.name}"`.
       - Any `.citem` with usage count `0` omits `role="button"`, `tabindex`, and `data-filter-*` attributes.
       - Activating an interactive `.citem` sets `activeFilter` (or clears it if already active for that exact `kind` and `id`) and switches the active view to `projects` so the RSE immediately sees the matching projects.
  2. **In `#v_projects` (`#projDetail`):**
     - In direct `rowTable` rows: the component cell wraps `compName(r.comp)` in `<span class="cchip" role="button" tabindex="0" data-filter-kind="comp" data-filter-id="${esc(r.comp)}">`, each `.dchip` receives `role="button" tabindex="0" data-filter-kind="data" data-filter-id="${esc(id)}"`, and each `.tchip` receives `role="button" tabindex="0" data-filter-kind="tech" data-filter-id="${esc(id)}"`.
     - In `uses` rows with `r.src` (rendered via `comboLabel(rr)` when `rr !== null`): `comboLabel(rr)` attaches `role="button" tabindex="0" data-filter-kind="comp" data-filter-id="${esc(rr.comp)}"` on the component label span, `role="button" tabindex="0" data-filter-kind="data" data-filter-id="${esc(id)}"` on each `.d` data span, and `role="button" tabindex="0" data-filter-kind="tech" data-filter-id="${esc(id)}"` on each `.t` technique span.
     - Clicking `.fromtag.is-link` or `.suppliestag .proj-link` sets `activeFilter = { kind: 'proj', id: targetProjId, label: pn(targetProjId) }` and sets `D.current = targetProjId`.
  3. **In `#v_relations` (`#relBody .edgetable`):**
     - In both supply rows (`s.from`, `s.to`) and tie rows (`t.a`, `t.b`) of `.edgetable`, the `Project A` and `Project B` `<b>` elements receive `class="proj-link" role="button" tabindex="0" data-filter-kind="proj" data-filter-id="${esc(projId)}"`.
